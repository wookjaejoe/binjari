# 캠핑장 빈자리 찾기

공공캠핑장 예약 사이트를 훑어 **예약 가능일자를 캠핑장 · 구역 · 객실 단위로** 한 화면에서 보여준다.
원 사이트는 날짜를 하나씩 골라야 잔여를 알 수 있어서, 어느 날 어떤 객실이 비는지 비교하기 어렵다.

현재 대상은 고성군 공공캠핑장 포털(`gwgs.pubcamping.kr`)의 7개 캠핑장이며,
캠핑장 목록은 포털에서 자동으로 발견한다.

## 실행

```bash
pnpm install
pnpm dev
```

http://localhost:3000

```bash
pnpm test        # 집계·날짜 경계 단위 테스트
pnpm typecheck
pnpm lint
```

## 왜 이 앱인가

숙박앱과 기존 캠핑 앱은 **어디를 갈지 먼저 고르고 → 날짜를 확인**한다. 대상이 이미 정해진
사람을 위한 순서다. 공공캠핑장은 반대다. 싸고 인기 많아 취소 자리를 노려야 하고,
날짜는 유연하지만 원하는 자리는 구체적이다("카라반4인, 아무 주말이나").

그래서 이 앱은 **조건을 선언하면 전체 답을 한 화면에 내놓는다.** 참고한 모델은 숙박앱이 아니라
[Google Flights의 Date Grid](https://traveldonesimple.com/travel-planning/transportation/flights/google-flights-guide/part-3-date-grid-price-graph/)다 — "언제가 싼가"를 격자로 답하는 그 구조에서
축만 "언제가 비는가"로 바꿨다. 예약은 [Campnab](https://campnab.com/faq)처럼 원 사이트로 넘긴다.

차별점은 세 가지다.

1. **커버리지** — 지자체 자체 예약 시스템. 대형 앱이 잘 붙지 않는 영역이다.
2. **정밀도** — "빈자리 있음"이 아니라 `카라반(특)6-3` 특정 동 단위로 지정한다.
3. **방향** — 여러 캠핑장 × 여러 구역 × 전 기간을 동시에 본다.

## 화면

상단 조건 바는 버튼 세 개로 접혀 있다 — **대상 · 숙박일수 · 체크인 요일**. 각각 누르면
시트가 올라온다. 숙박일수 시트는 그 일수로 조회할 수 없는 캠핑장을 미리 알려주고,
요일 시트는 일~토를 개별로 켜거나 프리셋(금·토 / 주말 / 평일)으로 고른다.

결과는 세 가지 형태로 볼 수 있다.

- **히트맵** — 달력과 같은 방향(행=주, 열=요일)에 농도를 얹었다. 칸마다 날짜와 열린
  자리 수가 함께 있고, 요일을 좁히면 나머지 열이 흐려지며 신호가 또렷해진다.
  열이 7개로 고정이라 조회 기간이 길어져도 칸 크기가 변하지 않는다.
- **목록** — 빈자리가 있는 날만 위에서 아래로. 칩은 잔여율이 낮은 순이라 귀한 자리가 먼저 온다.
- **표** — 행이 구역/객실, 열이 날짜. 한 행을 가로로 훑으면 그 구역의 시간 흐름이
  읽히고, 세로로 보면 같은 날 여러 대상이 비교된다.

대상 버튼을 누르면 시트에서 캠핑장 → 구역 → 객실을 3단계로 켜고 끈다. 구역을 펼치면 개별
객실이 나오고, 일부만 선택하면 그 객실들만으로 가용성을 다시 계산한다. 선택은 브라우저에 저장된다.

날짜를 누르면 상세 시트가 열리고 **예약 페이지 열기**로 이어진다. 원 사이트가 일정을 POST
폼으로만 받기 때문에 링크가 아니라 hidden 폼으로 넘기며, 새 탭에 해당 일정이 선택된 상태로 열린다.

디자인 토큰과 그 근거는 [DESIGN.md](DESIGN.md)에 있다.

## 구조

```
lib/providers/types.ts     예약 시스템이 구현해야 하는 인터페이스
lib/providers/pubcamping.ts pubcamping.kr 어댑터
lib/registry.ts            포털 등록부 · 캠핑장 자동 발견
lib/scan.ts                기간 전체 스캔 오케스트레이션 (동시성 제한 + TTL 캐시)
lib/availability.ts        선택 상태를 행·셀로 환산하는 순수 로직 (테스트 대상)
lib/policy.ts              테스트 구역 판별 · 기본 선택 크기 · 농도 단계
app/api/**                 브라우저용 프록시. 원 사이트에 CORS 헤더가 없어 서버를 거쳐야 한다
store/selection.ts         선택·보기 상태 (localStorage 유지)
```

스캔은 두 단계다.

1. **구역 스캔** — 날짜마다 1회 호출로 모든 구역의 잔여를 얻는다. 60일이면 60회, 1초 내.
2. **객실 스캔** — 구역을 펼치거나 일부만 선택했을 때만, 그 구역에 대해서만 돌린다.
   잔여가 0인 날은 응답이 비므로 건너뛴다.

두 결과 모두 서버에서 3분 캐시하고, 같은 키의 동시 요청은 하나의 작업을 공유한다.

## 캠핑장 · 포털 추가

같은 예약 시스템(pubcamping.kr)을 쓰는 다른 지자체라면 `lib/registry.ts`의 `PORTALS`에 한 줄 더한다.
그 포털의 캠핑장은 자동으로 발견된다.

```ts
export const PORTALS: Portal[] = [
  { id: "gwgs", host: "gwgs.pubcamping.kr", label: "고성군", provider: "pubcamping" },
  { id: "xxx", host: "xxx.pubcamping.kr", label: "○○군", provider: "pubcamping" },
];
```

특정 캠핑장을 숨기거나 이름을 다듬으려면 `CAMP_OVERRIDES`를 쓴다.
처음 방문 시 켜 둘 캠핑장은 `lib/defaults.ts`의 `DEFAULT_CAMP_IDS`.

예약 시스템이 아예 다른 곳(다른 솔루션을 쓰는 지자체, 국립공원 등)은
`CampProvider`를 구현한 어댑터를 하나 만들고 `PROVIDERS`에 등록한다.
화면·집계 코드는 인터페이스만 알고 있으므로 손댈 필요가 없다.

## 알아둘 것

- **조회 범위는 사이트가 정한다.** 각 캠핑장이 예약을 열어 둔 기간(`room_start_day` ~ `room_end_day`)과
  최대 숙박일수를 그대로 따른다. 캠핑장마다 다르고, 보통 한두 달 단위로 열린다.
  기간이 늘어나면 앱도 자동으로 늘어난다.
- 최대 숙박일수를 넘겨 조회하면 해당 캠핑장은 전 기간이 "예약 기간 아님"으로 표시된다.
- 조회 기간 내내 마감인 구역은 원 사이트가 객실 목록을 주지 않아 개별 객실을 고를 수 없다.
- **아직 운영 전인 캠핑장이 목록에 섞여 있다.** 예약 기간이 없으면 "예약 미오픈"(명파),
  기간은 있는데 실제 구역이 없으면 "예약 준비 중"(대진1리 — "결제테스트" 구역만 등록돼 있다)으로
  표시하고 선택할 수 없게 한다. 하드코딩이 아니라 매번 판정하므로 실제로 열리면 자동으로 켜진다.
- 이름에 "테스트"가 들어간 구역은 조회 대상에서 제외한다.
- 처음 방문 시에는 12면 이하의 소규모 구역만 켜 둔다. 대규모 사이트는 상시 여유가 있어
  "빈자리 찾기"의 신호를 덮기 때문이다 (`COMPACT_ZONE_MAX`).
- 실제 예약·결제는 원 사이트에서만 이뤄진다. 이 앱은 읽기만 한다.
